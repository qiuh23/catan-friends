# 随机、聊天与举报运维

> 现行站点方案：国内 `SITE_EDITION=cn`，固定建筑/艺术昵称且完全禁用玩家交流、交流处置及访问/连接安全审计，保留故障和游戏数据；海外 `SITE_EDITION=global` 保留自定义昵称/聊天。两站入口、身份与邀请码独立。国内需安装 `access_log off` 的 Nginx 模板和仅故障日志的轮转配置，停用本游戏旧审计任务；现有备份/磁盘故障监测继续保留，历史私有审计不删。下述旧聊天/昵称/安全审计行为仅适用于海外，历史部署快照不证明新方案已上线。构建、接收器更新与验证见 [站点策略](site-editions.md)。


本说明对应 schema 3 源码；首次应用需要更新主机运维脚本和仓库发布准备变量。创建 PR 不代表生产配置、部署或备案审核完成。当前线上回读见 [本轮记录](random-chat-report-2026-11-06.md)。

消息隐藏、替代昵称与受限成员 ID 是执行处置的最小标记，运行中房间继续保留；房间关闭后去掉这些明细，只留下防复活的关闭标记及尚未到期/保全的审计。审计每房间最多 1,000 条，达到容量时拒绝继续写入，不覆盖未到期/保全证据。Node 约 30 秒清理到期审计；Worker 按到期 alarm 清理。普通聊天在发布/存在检查和 alarm 中清理，快照始终过滤已过期消息。

90 天是此次选择的运行期限。适用网络日志义务仍须单独核实、配置和验收：[现行网络安全法](https://www.gjbmj.gov.cn/n1/2026/0421/c409088-40705863.html)区分网络运行/安全事件相关日志留存与内容处置；[个人信息保护法](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)第十九条要求在无其他法定期限时采用实现目的所需的最短保存期限。本 PR 没有据此宣称普通聊天须保存六个月，也没有实现/证明完整六个月网络日志、实名、备案受理、邮件响应时限或生产告警链路。

## 玩家举报

首页、设置和聊天均可进入“隐私 / 举报”。聊天显示 `#消息编号` 并提供单条举报入口；界面只在玩家打开时显示说明，不常驻覆盖棋盘。

邮件预填线路、房间、消息编号和时间，由玩家填写原因并亲自确认发送。没有后台自动发信、工单队列或 AI 审核。不要要求举报者提供恢复凭据、完整手牌或证件。记录缺失时应说明证据范围，不补造历史。

## 站长人工流程

1. 从确认的邮箱接收举报，核实线路、房间和消息编号，必要时先保全相关记录。只处理所需内容，按适用要求向有关部门报告。
2. 经 SSH 回环隧道或 HTTPS 使用 `scripts/stationmaster.mjs`；密钥仅放在当前受保护进程环境。不要把密钥放进 argv、URL、截图、页面或仓库。
3. 查看公开昵称、成员 ID、最近聊天与必要处置记录。接口不提供手牌、牌库、恢复摘要或随机流。
4. 人工核实后提交带理由的处置；独立记录先持久化，再清理公开视图、保存房间并广播。失败时不声称已经处理；重试沿用相同 `id`。
5. 通过原身份重连/刷新复核结果，向举报者作必要回复。结束保全目的后显式解除；不自动推定案件结束。

示例（JSON 从 stdin 输入，以下不含真实密钥）：

```powershell
'{"action":"inspect"}' | node scripts/stationmaster.mjs https://catan.magical-athlete-online.cn ABC234
```

可用操作：

```json
{"action":"inspect"}
{"action":"hide-chat","messageId":"从 inspect 取得的消息 ID","reason":"核实举报后隐藏"}
{"action":"reset-name","memberId":"从 inspect 取得的成员 ID","reason":"昵称不当"}
{"action":"restrict-member","memberId":"成员 ID","reason":"持续滥用"}
{"action":"restore-member","memberId":"成员 ID","reason":"复核后解除"}
{"action":"close-room","reason":"停止房间继续传播"}
{"action":"hold","eventId":"处置记录 ID","held":true,"reason":"具体保全依据"}
{"action":"hold","eventId":"处置记录 ID","held":false,"reason":"保全目的结束"}
```

工具会补一个操作 `id`。需要安全重试时自行提供原 `id`；审计内有该 ID 时不会再次执行。请求不接受其他字段。限制只针对这一房间内的游戏身份，不保证阻止换浏览器/新身份；房主不能调用站长接口。统一站长角色目前不区分多个管理员。

人工查看/处置采用字段白名单：时间、到期时间、操作 ID、站长角色、操作类别、必要目标及理由；隐藏消息时仅保留该消息昵称/文字作为证据，重置昵称时仅保留原昵称。原始请求、Authorization、凭据、完整游戏和随机状态不进入审计。通用错误和后台日志也不输出异常内容或完整对象。

## 随机与存档迁移

`room.version=3`，秘密随机流放在房间根字段 `random`；不会存入可投影的 `game` 对象。初始 256 位 key 和 96 位 nonce 来自 Web Crypto；ChaCha20 缓冲、计数器和偏移随房间一起保存。计数器耗尽或流无效时拒绝继续，不能自动换种子或回绕。

地图、港口、数字、发展牌 Fisher–Yates、两个独立骰子和按张数抢牌都使用同一私有流；整数采用拒绝采样去除取模偏差。基础地图最多尝试 10,000 次后明确失败，事务回滚，不返回违规地图；扩充数字仍按原 A..Zc 环绕规则跳过沙漠。先手仍是原入座顺序。

旧房间（version 1/2）首次加载时保留地图、资源、牌库、座位、规则、进度与身份，仅为后续随机动作建立一次安全流；原先 Math.random 的历史不可还原，不重新发牌或重新生成地图。旧聊天以旧房间活动时间补时间戳并受 7 天上限限制，不因重启刷新留存期限。存档已有流但损坏、空值或算法未知时失败，不当作旧档重新播种。

Node 先写临时文件再原子替换、成功后才确认；Worker 把房间、秘密流与下一 alarm 一并事务提交。房间操作和电脑动作失败后恢复原随机状态；成功请求重复先查回执再查棋盘版本。聊天独立序号/回执和玩家令牌桶不会改变棋盘 revision，也不会挤出游戏回执；玩家桶容量 5、每 2 秒补 1，随房间保存，重连/重启不重置。传输层的来源/连接防滥用限制仍保留。

## 发布前准备

1. 只更新 Catan 的 root 所有运维文件：`ops/deploy.py` 对应 `/usr/local/sbin/catan-friends-deploy`；`ops/backup.py` 对应 `/usr/local/lib/catan-friends-ops/backup.py`。保留既有所有者、权限、路径隔离。不要在已运行主机重新执行整套 bootstrap。
2. 更新前保留现有房间、配置和运维脚本的私有备份；更新后先验证备份兼容 version 1/2/3 和关闭 tombstone，归档同时包含 `snapshot/rooms`、`snapshot/moderation` 与受保护配置。Node 新增处置在 `DATA_DIR/moderation/房间码.json`；Worker 是原 CatanRoom 对象内独立 `moderation` 存储 key，不随 room tombstone 删除，不新增绑定或 DO migration。
3. 两端分别配置独立管理员密钥；Node 受保护 env 增补已确认邮箱与 90 天期限，Worker vars 已进入源码配置，密钥仍由 `wrangler secret put SECURITY_ADMIN_TOKEN` 或正式受保护流程设置。不要在终端回显密钥。
4. 确认首次 schema 3 发布的修复路线：旧版本没有新限流和处置语义，不能作为安全回滚目标。准备同 schema 的兼容修复版本；失败时保留数据并前向修复。
5. 完成准备后设置仓库 `CATAN_STATE_SCHEMA=3`；与 `CATAN_PRODUCTION_ENABLED=true` 同时满足才允许现有发布链运行。此 PR 不设置这些线上变量、不改服务器、不触发部署。
6. 正常发布后逐端核实前后端 SHA、`/api/security/contact`、未认证处置 403、真实玩家连接/聊天、重连与存档、目录/邀请、处置及独立站长权限。代码合并或 CI 成功本身不能替代这些验收。

## 回滚与恢复

发布包 `release.json.stateSchema=3`。更新后的 Node 接收器只接受这一格式，回滚前检查上个包同为 schema 3；Worker 记录旧不可变版本的 `STATE_SCHEMA=3` 标记，只允许安全版本回退，并继续核对当前版本确属本次尝试。旧接收器会拒绝新包，因此不能遗漏主机脚本更新。

普通回滚只切兼容代码，保留最新房间随机流、回执、玩家限流和独立处置。首次迁移没有兼容前版时明确拒绝自动降级，发布兼容修复版本；不要 force Worker 回滚、删除绑定、删随机字段或从备份覆盖刚确认的动作。

灾难恢复要停新操作并保存当前数据；把已校验的房间与处置记录一起恢复到隔离临时目录，先按当前时间清理到期内容、重新应用处置，再允许连接。处置记录比游戏副本新时优先应用，不能只恢复旧游戏绕过隐藏、限制或关闭标记。随机流回退会重用以前输出，不能作为普通发布回滚方案；恢复到较早进度涉及丢失动作，需单独明确恢复范围。

源码备份策略沿用最多 14 天及 256 MiB 上限，容量压力可能缩短实际备份窗口；这与 90 天在线处置记录不是同一承诺。历史备份需要受保护访问和轮转，恢复后先清理到期内容。保全证据不能只依赖短期滚动备份，站长须按实际案件要求保管、复核和解除。尚未验证生产磁盘权限、备份任务运行、邮件投递、告警接收或监管受理。
